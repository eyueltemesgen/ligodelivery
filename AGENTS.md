## Performance conventions

- Images: render through `StorageImage` (`src/lib/media.tsx`) with a `width` prop so the signed URL hits Supabase's image renderer. Signed URLs are cached per (bucket, path, width) and untransformed images are batch-signed; do not add per-image `createSignedUrl` calls elsewhere. `createSignedUrls` cannot carry transforms, so sized images sign individually by design.
- Toasts: import `toast` from `src/lib/toast`, never from `sonner` directly. `src/lib/toast.tsx` lazy-loads sonner and its `<Toaster>` host on the first toast, keeping ~14 kB gzip out of every route. `ToastHost` is mounted once in `src/routes/__root.tsx`.
- Public catalogue queries in `src/lib/queries.ts` carry explicit `staleTime` and a `limit` (`SHOP_PAGE_SIZE`, `PRODUCT_PAGE_SIZE`). Keep new list queries bounded; add `staleTime` for anything public.
- Indexes for hot read paths live in `supabase/migrations/20261004190000_performance_indexes.sql` (additive/idempotent, apply via Lovable/Supabase).

## Two-step checkout & payment method configuration
- `src/routes/checkout.tsx` is a two-step form: step 1 delivery details, step 2 payment method + tip + receipt. Payment is decided **before** the order is placed; it used to be deferred to the order page, which is why the platform appeared to "not ask for payment". Keys `checkout_step1`/`checkout_step2` drive the indicator and the step-1 button is only rendered in the sticky aside — do not add a second "Continue" button inside the form.
- The receipt is uploaded **after** `place_order` returns the order id, because `payment_proofs.order_id` is a FK to `orders`. A failed upload toasts `checkout_proof_failed` instead of throwing, so the order is never lost. The attach block is inside the non-cash branch, so `proofFile` is only used when `method !== "cash"`.
- `isMethodEnabled(id)` gates the method list: cash is always offered, an online method needs a `payment_<id>` settings row with `enabled !== false` **and** a non-empty `account`. Without this an unconfigured method showed as a selectable option that could never be paid. A `useEffect` falls back to `cash` if the selection becomes unavailable. This hook must stay **above** the `if (!user)` / empty-cart early returns or lint fails with `rules-of-hooks`.
- `payment_<id>.instructions` is now rendered to the customer. It is deliberately still filtered out of the generic `payDetails` key/value list (which excludes `enabled` and `instructions`) and shown separately, so the instructions prose is not treated as a copyable account field.
- **Admin payment settings had two bugs that made accounts unconfigurable, both fixed in `56f827a`:**
  - The form wrote `account_name`/`account_number`, but the reader (`checkout.tsx`, order page) and the seed migration use `holder`/`account`. Saving appeared to work and changed nothing.
  - `PaymentSetting` initialised its state from `value` once, and the settings query resolves *after* first render, so the fields were seeded from an empty object. Saving then wrote blank `account`/`instructions` over the stored value. Fixed with a `key` that flips when `settings[key]` becomes defined, which remounts the form after load.
  - `SettingsAdmin.save` now **merges** into the stored object (`{...settings[key], ...value}`) instead of replacing it, so keys the form does not edit (e.g. `extra_untouched`) survive. `enabled` is stored as a JSON boolean, not the string `"true"`.
- Live DB has **no** `payment_*` rows at all (only `contact, delivery, loyalty, platform, site_content`), and `settings_auth_read_payment` hides `payment_%` from `anon`. So checkout (authenticated) can read them, but an admin must actually enter account numbers before any online method appears. Verify with a CDP harness that stubs `settings` rather than expecting live rows.
- Harness gotcha: cart state lives in `localStorage` under `ligo.cart.v1` as a **flat array** of items each carrying `shopId`/`shopName` (not a `{shopId, items}` object), and React inputs need the native value setter plus a bubbling `input` event to register. `innerText` does not include input/textarea values — read `.value` directly.

## Payment gate & order tracking

- Orders must not be fulfilled before payment. The single gate is `public.approve_and_dispatch(uuid)`: it refuses to dispatch a non-cash order unless `payment_status = 'paid'` (set by the admin's "Mark payment as verified" action or a receipt approval), and it sets `app.order_internal = '1'` so the column guard allows the dispatch write. Never add a raw `orders.update({ status: 'dispatched' })` fallback — that would deliver an unpaid order.
- `orders_guard_update` blocks a non-admin from changing `status` on a non-cash order that is not paid (only `cancelled` is exempt), and blocks every non-admin write to `payment_status`/amounts/`rider_id`/`delivery_pin`. `accept_order` and `complete_delivery` therefore set `app.order_internal = '1'` before their updates. `complete_delivery` also requires the order to be `on_the_way`/`picked_up` and marks cash orders `paid`.
- Payment alone is not enough — the guard must also check **who** is writing the status. `20261005120000` exempted cash orders and never checked the actor, so any authenticated customer could `PATCH` their own cash order straight to `delivered` (verified live: customer self-delivered an order with `rider_id` NULL and `payment_status` `unpaid`, earning commission/payouts for a delivery nobody made). `supabase/migrations/20261005160000_order_fulfilment_authorization.sql` closes this: for non-admins, `confirmed`/`preparing`/`ready_for_pickup` require `owns_shop(shop_id)`, `accepted`/`arrived_at_merchant`/`picked_up`/`on_the_way` require the caller to be the assigned rider (`has_role(uid,'rider')`), `delivered` is RPC-only ("Deliveries are completed with the customer PIN"), `cancelled` requires the customer or shop owner, and any other transition raises. It also restores the commission columns on every non-admin write (including cancel) so a caller cannot forge them. When changing the guard, keep the admin/`app.order_internal` bypass or `approve_and_dispatch`/`accept_order`/`complete_delivery` break.
- All three RPCs are defined in the final migrations as `RETURNS void`, but the current code returns `public.orders`. `CREATE OR REPLACE FUNCTION` cannot change a return type, so the migration that fixes them must `DROP FUNCTION IF EXISTS public.<name>(<args>);` first (see `supabase/migrations/20261005120000_payment_gate_and_tracking.sql`).
- Customer live tracking needs the `riders_select_assigned` RLS policy: it lets a customer read the `riders` row for the rider assigned to their own order (`order.rider_id`). Without it the order page's `riders` query returns null and no marker shows. The order page also polls the rider every 15 s and subscribes to `riders` realtime updates as a fallback.
- Leaflet markers must use `L.divIcon`, never the default icon. `L.marker(...)` with no `icon` resolves to `marker-icon.png` relative to the Leaflet CSS, but Vite emits no such asset (the URL 404s) so the marker renders as a broken image — this is why the customer's rider marker (and the `LocationPicker` pin) never appeared on the tracking map. `OrderMap.tsx` and `LocationPicker.tsx` now draw a coloured `divIcon`; `RiderTrackingMap.tsx`/`LiveMap.tsx` already did.
- RLS policy recursion trap: `orders_select_dispatch_pool` is a policy ON `orders` that reads `riders`, so any policy ON `riders` that reads `orders` closes a cycle and Postgres fails **every** `orders` SELECT with `42P17 infinite recursion detected in policy for relation "orders"` — the customer order list errors and the tracking page renders blank. Never put a `SELECT ... FROM public.orders` directly inside a `riders` policy. Instead expose the check through a `SECURITY DEFINER` function (`public.customer_can_see_rider(uuid)`), which RLS does not re-evaluate (same pattern as `is_admin`/`has_role`). The naive policy shipped in `20261005120000` and is corrected by `20261005130000_fix_riders_tracking_recursion.sql`; both must be applied for tracking to work without breaking order reads.
- UI mirrors the gate so users get a disabled button and an explanation instead of a raw DB error: `admin.ops.tsx` (Approve & Dispatch) and `merchant.tsx` (accept/prepare) both disable the action when `payment_method !== 'cash' && payment_status !== 'paid'`.
- The order detail page (`account.orders.$orderId.tsx`) presents payment before tracking: the map renders only once `paymentSettled` (`payment_method === 'cash' || payment_status === 'paid'`). While unsettled it shows `od_tracking_locked` instead of the map, so a customer cannot watch a rider before paying.


## Rotating banners & carousels
- One reusable rotator lives in `src/components/ligo/RotatingCarousel.tsx`: `RotatingSlides` (full-width slides, translateX track, autoplay) and `RotatingRow<T>` (horizontally scrollable card row that pages one screen at a time). Both default to a 3 s autoplay interval (`intervalMs`, overridable per call site), pause on hover/focus/drag and honor `prefers-reduced-motion` (no autoplay, no smooth scroll). Use these instead of writing new carousel logic.
- `RotatingSlides` renders a single child as-is (no controls), so it is safe for a placement that only has one banner.
- Touch gotcha: a horizontal touch drag makes the browser fire `pointercancel`, not `pointerup`. Both rotators pause on gesture start, so both must also resume on `pointercancel`/`touchcancel` — otherwise the carousel stays frozen for the rest of the session after the first swipe on a phone (verified live: `scrollLeft` stopped changing entirely). Keep those handlers when touching the pause logic.
- `pointercancel` ordering gotcha (swipe carousels that compute a delta): the browser fires `pointercancel` **before** `touchend` on a horizontal drag (verified live via CDP: `touchstart, touchmove, pointercancel, touchend`). A component that stores the touch origin in a ref must therefore NOT clear that ref in `onPointerCancel` — otherwise `onTouchEnd` sees a null origin and every swipe is silently ignored while autoplay still resumes, so it looks like "swipes just don't work". Resume autoplay in `onPointerCancel`, but only clear the origin in `onTouchCancel` (a genuine cancel has no following `touchend`). `RotatingCarousel` gets away with clearing it because it has no swipe-delta path (it scrolls natively). See `ServiceCategoryBanner` in `src/components/special-moments/ServiceCards.tsx`.
- `BannerSlot` rotates every active banner for a placement through one slot rather than stacking a grid, so a placement with N banners occupies one slot on the page. Banners are DB-driven (`public.banners`, `bannersQuery(placement)` in `src/lib/content.ts`).
- The homepage hero (`src/routes/index.tsx`) renders `home_hero` banners through `AdCarousel` (`src/components/ligo/AdCarousel.tsx`, restored from the `fix/payment-gate-and-tracking` line): a 3 s cross-fade overlay banner with a "SPONSORED" badge, CTA pill, title/subtitle scrim and bottom-centre dot indicators, holding 8 s after a manual swipe/tap. It is hidden when there are no `home_hero` banners, falling back to the የኔ Go monogram tile. Do not swap it back to the plain `RotatingSlides` list.
- Special Moments hub (`special-moments.index.tsx`) hero is a full-bleed image carousel from the `special_moments` banner placement; when no such banners exist it falls back to the `ServiceCategoryBanner`. The "Browse by category" section also uses `ServiceCategoryBanner`, while the featured-services row still uses `RotatingRow`. The homepage "Make every moment count" strip uses `ServiceCategoryBanner` too.
- `ServiceCategoryBanner` (`src/components/special-moments/ServiceCards.tsx`) is the auto-rotating category banner used on the Special Moments hub **and** the homepage "Make every moment count" strip. Its system (as merged in PR #30, `e49189be`) is a `translateX` track that slides horizontally, a `from-black/80` scrim, a `smi_badge` pill plus an availability pill ("N available" / "Coming soon"), the category name/tagline, and round pill indicators bottom-right. It keeps its own `useState`/`useEffect` (5 s default, `clearInterval` cleanup, pause on mouse hover/focus, swipe via `touchend`); do not swap it to the hero's cross-fade/bottom-centre-dot system. Passing `counts` makes it authoritative — a category absent from the map renders "Coming soon" (0), so always build the map over every category.
- Storage folder gotcha: the `ligo-media` read policy only allows folders `categories, shops, products, offers, banners, branding, merchants`. The service-category uploader writes to `services/categories/...`, which was never permitted, so those objects are unreadable (signed URL 404) and the upload is rejected — every service/category image renders as a placeholder. `20261005180000_special_moments_hero_banners.sql` adds `services` to the policy and seeds `special_moments` banners from `home_hero`. Add any new upload folder to that policy too.
- Carousels set `aria-roledescription="carousel"` + a distinct `aria-label` per region. Keep the labels distinct — two regions with the same label are ambiguous for screen readers. Keys used: `banner_carousel_aria`, `carousel_show`, `smi_categories`, `smi_show_categories`, `smi_show_services`, `home_moments_title`.

## Carousels must not stop advancing (`RotatingCarousel.tsx`)
- `RotatingRow`/`RotatingSlides` back the home hero, `BannerSlot` placements and the Special Moments hero. Two things silently froze them, both fixed in `4ca3a16`:
  - **Touch latch.** Hover-pause used `onMouseEnter`/`onMouseLeave`. Touch devices synthesise a `mouseenter` around a tap; if no `mouseleave` follows, `paused` latches `true` and autoplay never resumes. Hover pause now runs through `onPointerEnter`/`onPointerLeave` and ignores events whose `pointerType !== "mouse"`. Do not reintroduce raw `onMouseEnter` pause handlers here.
  - **Reduced motion.** `useAutoplay` used to bail out entirely under `prefers-reduced-motion: reduce`, so those users got a banner that never changed. Autoplay now always runs; reduced motion only drops the slide animation (`transition-none`). Never gate the *advance* on a motion preference — gate only the animation.
- `useAutoplay` holds `advance` in a ref and depends on `[active, intervalMs]` only. Keeping the callback in the dep array tears the interval down on every render and can starve rotation on a page whose queries keep resolving.
- Reproduce/verify with a headless Chromium CDP script at 390×844: dispatch `Input.dispatchTouchEvent` (touchStart + touchEnd) on the hero, then sample `translateX` every 1.5 s. Old code stayed on slide 0 for 16 s; fixed code cycles 0→1→2.
- Deployment gotcha: `ligodelivery-novexa4.vercel.app` serves an **older** build than `ligodelivery.vercel.app` (no `RotatingCarousel` chunk at all). When a fix "isn't live", check which alias the user is on before re-debugging the code.

## Shopping assistant (floating chat bubble)
- Customer-facing guide, **not** checkout. It answers via read-only, server-executed tools and hands off to the existing shop/cart/checkout flow. It never places, changes, cancels or pays for an order.
- Files: shared client-safe types/config `src/lib/assistant.ts` + `src/lib/assistant-config.ts`; server tools `src/lib/assistant.server.ts` (`.server.ts` keeps server-only imports out of the browser bundle); the single POST endpoint `src/lib/assistant.functions.ts` (`askAssistantFn`, tool-calling loop against the OpenAI-compatible Lovable AI Gateway); optional-auth middleware `src/integrations/supabase/optional-auth-middleware.ts`; UI `src/components/assistant/{AssistantProvider,ShoppingAssistant,AssistantResults}.tsx`.
- Provider + island are mounted in `src/routes/__root.tsx`; `SiteHeader.tsx` has a second trigger (`ai_header_label`) next to `ThemeToggle`. `ShoppingAssistant` is lazy (`React.lazy`) so the panel stays out of the initial bundle — keep it that way.
- The **no-invented-numbers** guarantee has three layers: (1) the system prompt forbids stating any figure not in a tool result; (2) every price/fee/distance/status is rendered from the tool JSON in `AssistantResults.tsx` via `ETB`/`formatDistance`/`STATUS_LABEL_KEY`/`pricingLabel`, never from prose; (3) `applyNumericGuard` in `assistant.functions.ts` blanks prose that quotes `ETB`/`birr`/`km` in a turn where no pricing tool ran, and surfaces a translated note instead of an empty bubble.
- Tools are dispatched from a fixed allow-list in `runTool` — never dynamically. Delivery fees come from the existing `public.calculate_delivery_fee` RPC, copied verbatim. **Every tool runs on the caller's own client** (`ctx.supabase`) — the assistant deliberately does **not** use `supabaseAdmin`/`client.server.ts`: that module throws at first property access when `SUPABASE_SERVICE_ROLE_KEY` is unset, which is exactly the deployed case (published builds have shipped without server env vars, hence the baked-in public fallback in `vite.config.ts`). The RPC is granted to `authenticated` and revoked from `anon` by design, so a signed-in customer gets a real quote and an anonymous visitor gets a typed `error` failure — the same behaviour as `src/lib/delivery.ts`. Do not reintroduce the service-role client here. Order lookup is scoped to `customer_id = userId` **and** the caller's RLS session; anonymous callers get a typed sign-in result.
- `optionalSupabaseAuth` mirrors `requireSupabaseAuth` but proceeds anonymously instead of throwing, and still verifies a present token with `getClaims`. Anonymous visitors get an RLS-enforced publishable-key client, not the service-role client.
- **Deploying off Lovable needs a model key, because only Lovable injects one.** `LOVABLE_API_KEY` is a Lovable Cloud project secret; a Vercel (or any other) deployment has it unset, so `assistantApiKey()` returns null and the assistant answers with the typed `ai_unavailable` note while its server function still returns **HTTP 200** — so it looks like "the assistant is broken", not "a key is missing". Reproduced live on `ligodelivery.vercel.app`. Fix: set a model credential in the host's environment (`GEMINI_API_KEY`, or `LOVABLE_API_KEY` if you hold its value). A real secret must never be baked into the bundle, so this cannot be a code fix.
- **The public backend coordinates are baked, deliberately and safely.** `src/lib/public-env.ts` is the single source of truth for `PUBLIC_SUPABASE_URL` / `PUBLIC_SUPABASE_PUBLISHABLE_KEY`, shared by `vite.config.ts` (which defines the client's `VITE_*` values) and `optional-auth-middleware.ts` (which needs them as `SUPABASE_URL` / `SUPABASE_PUBLISHABLE_KEY`). A host that sets only the `VITE_*` pair, or neither, used to leave the server with `supabase: null`, so every assistant tool returned an error result — the Vercel failure above. Baking them exposes nothing new (both are already sent to every browser) and the middleware still builds an **RLS-enforced** client from the publishable key, so an anonymous caller reads only what a signed-out browser could. It is not a service-role key. Keep this file free of secrets, and do not "fix" the fallback by reaching for the service-role client.
- Env: the model credential is provider-neutral and resolved at call time by `src/lib/assistant-config.ts`. Keys are tried in order `LOVABLE_API_KEY`/`LOVABLE_KEY` → `GEMINI_API_KEY`/`GOOGLE_API_KEY`/`GOOGLE_GENERATIVE_AI_API_KEY` → `DEEPSEEK_API_KEY` → `ASSISTANT_API_KEY`/`OPENAI_API_KEY` (all trimmed). **The key that resolves selects the default endpoint and model**, so key and endpoint cannot disagree: a Lovable key implies `https://ai.gateway.lovable.dev/v1` + `openai/gpt-5.5`, a Gemini key implies `https://generativelanguage.googleapis.com/v1beta/openai` + `gemini-3.8-flash`, a DeepSeek key implies `https://api.deepseek.com` + `deepseek-flash`. `ASSISTANT_BASE_URL` and `ASSISTANT_MODEL` override; when only `ASSISTANT_BASE_URL` is set the model is derived from that host. When no key is configured the function returns a typed `ai_unavailable` note (verified live) rather than erroring.
- **Default provider is the Lovable AI Gateway**, because that is how this project is deployed: Lovable Cloud injects `LOVABLE_API_KEY` as a project secret and bills it against the Lovable plan, so there is no separate model account to fund. The gateway is OpenAI-compatible and was confirmed live (`401 Missing API key`, so it accepts `Authorization: Bearer`). `openai/gpt-5.5` is the model the feature originally shipped with. `LOVABLE_API_KEY` is tried **first**, so a Lovable deployment needs no env configuration at all; a keyless deployment still targets the Lovable URL and degrades to the typed `ai_unavailable` note.
- **Provider choice is a one-line change, and the alternatives were measured.** Self-hosted open models (`qwen2.5:3b`, `llama3.2:3b`, `qwen3:4b`, `qwen2.5:7b` via Ollama) all **failed tool calling in Amharic** on this repo's own tool schema — zero calls, or the wrong tool — and their Amharic output was garbled or invented (`እናንዉ`, `ባለጀመሪያ`); `llama3.2:3b` never wrote Amharic at all. `gemini-3.8-flash` calls tools correctly in Amharic *and* Afaan Oromo and writes fluent Amharic. Whichever model is used, do not "simplify" to a small local one: a model that answers from memory instead of calling the fee tool **will invent delivery prices**, which is the exact failure the design exists to prevent.
- **The request shape is provider-specific, and the Lovable shape is not negotiable.** The platform's own "Fixed AI model settings" commit (main, `6ece9e7`) established that `openai/gpt-5.5` **rejects a custom `temperature`** and that tool calling on chat completions **requires `reasoning_effort: "none"`**; the follow-up `59bc76b` removed `ASSISTANT_TEMPERATURE` as dead code for exactly that reason. `assistantTemperature()` and `assistantReasoningEffort()` therefore derive from the resolved endpoint: the Lovable path sends **no temperature** and `reasoning_effort: "none"`, while Gemini/DeepSeek send `temperature: 0.3` and no `reasoning_effort`. Sending a field to the provider that rejects it **fails the whole call** rather than degrading, so none of these may be made unconditional. Override with `ASSISTANT_TEMPERATURE` / `ASSISTANT_REASONING_EFFORT` if a provider changes.
- **Do not "restore" a temperature on the Lovable path.** A later commit briefly did, reasoning that the original `3e6674c` shipped `temperature: 0.3` and that the `reasoning_effort` requirement was unverified. Both were wrong: `3e6674c` predates the platform's fix, and the requirement was verified by Lovable's own commit. Check `git log origin/main -- src/lib/assistant-config.ts` before changing this file — the platform edits it directly, so local reasoning about an older commit can silently revert a real fix.
- **Gemini specifics** (only relevant if switched to). The OpenAI-compatible shim is at `/v1beta/openai` (not `/v1beta`). `gemini-2.5-flash` is **retired for new accounts** (404 pointing at `gemini-3.8-flash`). Free-tier quota is tiny — **20 requests/day** for `gemini-3.8-flash`, and each assistant answer costs 2+ model calls because of the tool loop — so it needs billing, or `gemini-3.1-flash-lite` (separate, larger free quota). Gemini returns `extra_content.google.thought_signature`; it is **safe to drop** when rebuilding the assistant turn for the tool loop (verified both ways), so `ChatMessage` needs no change. Transient `503 "high demand"` is common on that endpoint.
- **Catalogue is Latin/English, so Amharic searches must be translated first.** Shops and products are stored with English names (`Bishoftu Burger House`), so searching the raw Amharic term (`በርገር`) matches nothing and the assistant answers "couldn't find anything" in perfect Amharic. System prompt rule 7 tells the model to translate the search term to English before searching, then answer in the customer's language. If multilingual search regresses, check this rule first.
- **DeepSeek specifics.** The legacy `deepseek-chat` / `deepseek-reasoner` model names were **retired 2026-07-24 and now return errors** — use `deepseek-flash` (or `deepseek-v4-pro`). The V4 models **default to thinking mode**, which is costly and historically unreliable with tool calls, so `assistantThinking()` sends `thinking: {type:'disabled'}` — but only for a `deepseek.com` host, because the parameter is DeepSeek-only and is a 400 anywhere else. Override with `ASSISTANT_THINKING=enabled|disabled`. DeepSeek's own notice also warns that function calling can produce *looped calls or empty responses*: `ASSISTANT_MAX_TOOL_ITERATIONS` caps the loop and the exhausted-budget branch returns the collected cards without another model call, so a loop degrades to data rather than hanging.
- **A direct answer must not be decorated with the "no answer" note.** When a turn produces no tool calls the loop used to append `ai_no_answer` ("I'm not sure about that one") unconditionally, which stapled a disclaimer onto good prose — e.g. a correct "which shop do you mean?" reply about delivery fees. The note is now added only when the turn yields neither cards nor prose. Keep that guard: it is the difference between a confident answer and one that contradicts itself.
- **Deployed assistant needs three env vars.** `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` (for the tools — *not* the `VITE_*` names `vite.config.ts` bakes in) and the model key. With the Supabase pair missing, `optionalSupabaseAuth` logs a warning and passes `supabase: null`, so every tool returns `ai_unavailable` — indistinguishable in the UI from a missing model key.
- `ASSISTANT_REASONING_EFFORT` is sent **only when set** — reasoning models need `none` for tool calls to be emitted, but non-reasoning models reject the field, so sending it unconditionally is a 400.
- **Supabase has no hosted chat-completions API** — its `Supabase.ai` runtime does embeddings only (`gte-small`) plus experimental self-hosted Llama/Mistral, and Supabase's documented pattern is an Edge Function *proxying* an external provider. So the split is: Supabase holds the data and runs the read-only tools, and the LLM stays behind the one OpenAI-compatible endpoint in `assistant-config.ts`. Do not look for a `supabase.ai` chat model; there isn't one.
- Because `assistant.functions.ts` also ships to the client bundle, `assistant-config.ts` must never read a secret at module scope — every env value is read inside a function.
- **Required server env, and a confusing failure mode.** The tools run through `optionalSupabaseAuth`, which reads `SUPABASE_URL` + `SUPABASE_PUBLISHABLE_KEY` from `process.env` (note: `VITE_SUPABASE_*`, which `vite.config.ts` bakes in for the browser, are **not** what the server middleware reads). When they are absent the middleware logs `[assistant] Supabase env vars missing; continuing without a client` and sets `supabase: null`, so `runTool` returns `ai_unavailable` for **every** tool. That is indistinguishable in the UI from a missing model key, which makes it a costly red herring: check the server log for the middleware warning before blaming the model provider. A deployed assistant needs `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` **and** the model key.
- Verified against the live project: every tool's exact select list resolves (`SHOP_COLUMNS`, `PRODUCT_COLUMNS`, `loadHours`, `service_categories`), and `calculate_delivery_fee` returns `permission denied` to anon as designed. `shop_hours` columns are `opens_at`/`closes_at`, **not** `open_time`/`close_time` — an easy wrong guess.
- i18n: all copy is `ai_*` keys in en/am/or (keys `ai_launcher_label` on the floating bubble and `ai_header_label` on the header trigger must stay distinct — two buttons sharing one aria-label is ambiguous). Server-side notes are `noteKey`s resolved client-side, so no English leaks from the tools.
- **Reply language is prompt-enforced, not just a trailing hint.** The client sends `language` and the server renders `LANGUAGE_RULE[language]`; a bare "Reply in Amharic" at the end of the prompt was not enough — the model mirrored the customer's script and then told them it "cannot respond in Amharic/Oromo". Keep the directive stated early, restated last via `REMINDER — …`, and paired with an explicit "you are fully able to write Amharic" line plus a "keep shop/product names verbatim" instruction. Do not collapse it back to a single trailing sentence.

## Customer order-status notifications
- Merchants and riders could not notify customers: the `notifications` INSERT policy is `WITH CHECK (user_id = auth.uid() OR is_admin())`, so a shop owner or rider inserting a row for the customer was rejected — and `notify()` never checks the error, so it failed **silently**. The customer watched "Confirmed" while their food sat ready at the counter.
- Fix is the `notify_order_status(_order_id, _title, _body)` SECURITY DEFINER RPC (`supabase/migrations/20261006100000_notify_order_status.sql`), which authorises by `is_admin() OR owns_shop(order.shop_id) OR (order.rider_id = auth.uid() AND has_role(uid,'rider'))` and always writes to `order.customer_id`. Do **not** "fix" this by relaxing the INSERT policy to `user_id <> auth.uid()` — that lets any signed-in user notify anyone. Client helper: `notifyOrderStatus()` in `src/lib/orders.ts`.
- `notify()` is still correct for admins (`admin.ops.tsx`, `admin.riders.tsx`) because `is_admin()` satisfies the policy.
- Riders/merchants change order status through **two** paths and both must notify: direct `orders.update({ status })` (`merchant.tsx` `advance`, `rider.index.tsx` `setStatus`) and the `accept_order` / `complete_delivery` RPCs. The RPC paths are easy to miss — they change status server-side, so they need an explicit `notifyOrderStatus` call after the RPC succeeds.
- A new RPC must be added to `src/integrations/supabase/types.ts` `Functions` by hand; generated types are not regenerated here, so `supabase.rpc("notify_order_status", …)` fails `tsc` until it is.
- Header badge: `SiteHeader.tsx` reuses `accountSummaryQuery` for the unread count and subscribes to `notifications` realtime to invalidate `["account-summary", uid]`. Without the subscription the badge only updates on reload, which defeats the point for a customer who is not on the notifications page.
- Verify the RPC's authorization with `scripts/verify/notify-rpc-sql.mjs` (PGlite runs the real migration on real Postgres) — a SECURITY DEFINER guard cannot be checked by a stubbed browser test. Browser wiring: `scripts/verify/merchant-notify.mjs` and `rider-notify.mjs`.
- Harness gotcha: a harness that stubs a fake session in `localStorage` poisons the shared browser profile — every later request 401s and unrelated harnesses fail confusingly. Run stub-session harnesses in their own `Target.createBrowserContext`, or clear the profile between runs.

## Honest shop ratings
- `shops.rating` shipped as `numeric(2,1) NOT NULL DEFAULT 4.5` — a placeholder no customer could influence. `20261005150000_reviews.sql` added real aggregates but kept the seed as a fallback (`COALESCE(avg, s.rating)`), which was reasonable while `reviews` was empty and is not now: on the live DB **6 of 7 shops advertised "4.5" from `rating_count = 0`**. A fabricated star rating is the most damaging thing on the storefront — a customer who learns the stars are fake stops believing the reviews we just shipped.
- `20261006110000_honest_shop_ratings.sql` clears the seed for shops with no reviews, sets the column default to 0 (products already did this), and changes the aggregate fallback from `s.rating` to `0` so deleting a shop's last review no longer resurrects a stale average. Additive/idempotent.
- **Always gate a rating on `rating_count > 0`, never on `rating > 0`.** The seed made `rating > 0` true for shops with zero reviews. `shops.$shopId.tsx` rendered the bare seeded number on its `else` branch, and `AssistantResults.tsx` gated on `shop.rating > 0` — both showed 4.5 for unreviewed shops. Products were already correct because `products.rating` defaults to 0.
- The fabricated constant also corrupted **ranking**: `queries.ts` and `assistant.server.ts` sort by `rating DESC`, so unreviewed shops outranked shops with a real (lower) average. Ordering now carries a `rating_count DESC` tiebreaker, and the migration makes the stored value honest so the first key means something. Keep the tiebreaker whenever you touch that sort.
- The assistant must not be handed an unearned number: `toShop` in `assistant.server.ts` gates `rating` on `ratingCount > 0`, so the value in the tool JSON is 0 rather than 4.5. That keeps the no-invented-numbers guarantee independent of whether the migration has been applied yet.
- UI copy: an unrated shop reads "New" (`common_new`), which already existed in all three locales — no new i18n keys were needed for this one.
- Harnesses: `scripts/verify/ratings-sql.mjs` (PGlite: seed cleared, real average kept, last-review deletion leaves 0, idempotent) and `scripts/verify/ratings.mjs` (live DB: reads the rows, then asserts the page matches them).

## Rewards & Referrals (loyalty)
- Migration: `supabase/migrations/20261006090000_loyalty_and_referrals.sql` (additive/idempotent). Apply before the matching build — reads degrade to `LOYALTY_FALLBACK` (disabled) and checkout simply hides the redemption control until it is applied, so nothing breaks, but no points accrue.
- Tables `loyalty_wallets` (one per user: `points`, `lifetime_points`, `referral_code`, `referred_by`, `referral_credited`) and `loyalty_ledger` (`kind` in `earn|redeem|referral_bonus|referral_welcome|signup_bonus|admin_adjust`). Rates live in `settings` key `loyalty`, read only through `public.loyalty_config()` — never hardcode a rate in a component.
- **`loyalty_credit` is the only writer of a balance, and the ledger row is the idempotency key.** It inserts the ledger row FIRST (`ON CONFLICT DO NOTHING ... RETURNING id`) and returns early when the row already existed, so a re-delivered order cannot pay out twice. Do not move the wallet `UPDATE` before that check — the original ordering double-credited. Debits pass negative points and raise on an insufficient balance; `points >= 0` is also a CHECK constraint.
- Earning is a trigger on `orders` (`orders_loyalty_on_delivered`, `AFTER UPDATE OF status`, `WHEN NEW.status='delivered' AND OLD.status IS DISTINCT FROM 'delivered'`). Points come from `subtotal` only — the delivery fee and tip are not purchase value.
- **Referral linking happens once, in `handle_new_user`, from `raw_user_meta_data->>'referral_code'`.** `register.tsx` puts the `?ref=` code into the signup metadata so it survives email-confirmation signups (no session yet). It is deliberately NOT a `place_order` argument: a code supplied at checkout could be applied to an account that never used it and re-applied order after order. The referrer/referee bonus pays on the referred customer's first *delivered* order, guarded by `referral_credited` plus the ledger unique index.
- **Redefining `handle_new_user` means preserving every existing branch.** The admin bootstrap (`admin_bootstrap` → first account becomes admin) and the rider/merchant role branches came from later migrations; dropping them silently stops the first signup becoming admin. Only the wallet + referral link are new here.
- `place_order` gained one optional trailing arg, `p_redeem_points int DEFAULT 0`. Because `CREATE OR REPLACE` cannot change a signature, the migration must `DROP FUNCTION` the old form first (see the overload note below) — and the `REVOKE`/`GRANT` lines must list the new signature exactly, or the migration errors.
- **The live DB's `place_order` has drifted from this repo, and the migration must drop *every* overload.** The live function also carried `p_delivery_duration_s` and `p_road_distance_km` (13 args), from a road-routing migration that exists in no file here; `orders` likewise carries `delivery_duration_s`/`delivery_source`. Those two extra params are also visible in `src/integrations/supabase/types.ts`, which was generated against the live DB — that file is the only record of them. The original single-signature `DROP FUNCTION IF EXISTS public.place_order(…11 args…)` therefore removed only the 11-arg overload and left the 13-arg one behind. Two overloads differing solely in trailing optional arguments make every short-form call ambiguous: `place_order(a,b,c)` fails with `function ... is not unique`. PostgREST resolves the app's named-argument call by exact parameter set, so checkout kept working and the breakage stayed latent. The migration now drops every overload in a `DO` loop over `pg_proc`. When you touch `place_order`, keep that loop — and if the road-routing migration ever lands in this repo, reconcile the two signatures rather than adding a third overload.
- Redemption caps at `max_redeem_percent` (default 20%) of `subtotal + delivery_fee − discount`, which is the same base the client uses, so the slider offers a reachable maximum. `src/lib/loyalty.ts` `maxRedeemablePoints`/`pointsForSubtotal` mirror the server for display only; the server re-validates and wins. The slider snaps to 0 or `min_redeem_points` — nothing between is valid.
- UI: `src/routes/account.rewards.tsx` (balance, shareable code, invite count, how-it-works, ledger), checkout redemption block in `src/routes/checkout.tsx`, admin tab `RewardsAdmin` (`?tab=rewards` in `admin.ops.tsx`). Data layer `src/lib/loyalty.ts` (client-safe, graceful degradation via `isMissingTable`).

## Installable app (PWA)
- `public/manifest.webmanifest` alone does **not** make the site installable: Chrome/Android also requires a registered service worker with a `fetch` handler, and iOS has no install event at all. `public/sw.js` + `src/lib/pwa.ts` + `src/components/ligo/InstallPrompt.tsx` close that gap.
- **Register on `readyState === 'complete'`, not a bare `load` listener.** The root component hydrates *after* `load` has already fired on a server-rendered page, so `window.addEventListener('load', …)` never ran and the worker was silently never registered (verified: `getRegistrations()` returned 0 while a manual `register()` succeeded). `registerServiceWorker()` is called from a `useEffect` in `RootComponent` so it never runs during SSR.
- The worker caches **only** same-origin build assets (immutable `/assets/*`, hashed) and a 4-file offline precache. Navigations are network-first with `offline.html` as the fallback. Never make navigations cache-first: the app is server-rendered and a cached HTML shell would serve stale prices and stale order status.
- **The API and auth must never enter a cache.** `BYPASS` matches `/api/`, `/auth/`, `/rpc/` and `supabase.co`; only `GET` is handled, and only `response.type === 'basic'` (same-origin) responses are stored. Audited live across `/`, `/shops`, `/offers`, `/special-moments`, `/account/rewards`: 74 entries, all same-origin assets, zero Supabase/auth/RPC entries. Preserve that invariant — a cached Supabase response could show one customer another's data.
- `offline.html` is deliberately self-contained: the locale chunks are unreachable offline, so its five strings and the en/am/or switcher are inlined, and it mirrors the app's `ligo-lang` localStorage key plus the same browser-language default rule.
- The install card hides when already standalone, after dismissal (`yene.install.dismissed`), and when the browser offers nothing. iOS gets Share → Add to Home Screen instructions instead of a button, since `beforeinstallprompt` does not exist there. ## Search: match the description, and quote the term
- `searchQuery` in `src/lib/queries.ts` used `.ilike("name", ...)` only, so a term living in the description was invisible: the live DB had "Doro Wat" described as "Slow cooked chicken stew" and "Sunflower Oil 3L" described as "Cooking oil", both unfindable by the obvious query. It now matches `name` **or** `description` on shops and products, plus category names, and products embed `shops(name)` so a result says where to order it.
- **The term is interpolated into a PostgREST `or=(...)` filter, which is its own grammar.** A bare comma splits the logic tree and a bare parenthesis ends it, so a search for `Sambusa, 5` hard-failed with **PGRST100** and rendered an empty page (the error was swallowed by `(s.data ?? [])`, so it looked like "no results"). Values are therefore double-quoted: `name.ilike."*term*"`.
- **Do not add the outer parentheses yourself.** `supabase-js` `.or()` wraps the string in parentheses, so passing `(a,b)` produces `or=((a,b))` and every request 400s. Pass `a,b`.
- A double-quoted value cannot contain a raw quote or backslash (they escape the quoting), and LIKE metacharacters would over-match, so `SEARCH_PATTERN_STRIP` removes `"`, `\`, `%`, `_` and `*` before the term is embedded. Commas and parentheses are deliberately kept - they are safe once quoted, and `Sambusa (5` should match `Sambusa (5 pcs)`. A term made only of stripped characters returns early instead of matching the whole catalogue.
- `categories` has **no `description` column** (unlike `shops`/`products`), so it takes a name-only filter; sharing the two-column `or` there fails with `42703 column categories.description does not exist`.
- `ProductCard` gained an optional `shopName` (typed `string | undefined` because `exactOptionalPropertyTypes` is on) and falls back to `search_no_description` for a blank description. New keys `search_categories` / `search_no_description` are in all three locales.
- Verify with `/tmp/verify_search.mjs` (Node + CDP, no stubs - every query runs against the live project). It asserts the description match, the comma/parenthesis terms, that a bare `*` matches nothing, and zero 400s from Supabase, which is what catches the double-parenthesis class of bug.
## Migrations are NOT replayable from scratch (verified 2026-10-19)
- The committed set under `supabase/migrations/` is documented as "additive and idempotent", but that only holds when applied **incrementally** to a database that already has the earlier migrations. Replaying all 37 files in order onto an empty database fails at `20260901235243_...`: it does `CREATE POLICY shop_hours_public_read`, which `20260819181500_...` already created, with no preceding `DROP`. Several other files re-create policies/triggers the same way.
- `CREATE OR REPLACE FUNCTION` also cannot change a return type, so a replay needs `DROP FUNCTION` first for `accept_order`/`approve_and_dispatch`/`complete_delivery` (the `orders` → `void` → `orders` flip documented in the payment-gate section).
- To replay from scratch, preprocess each file: prefix `CREATE POLICY`/`CREATE TRIGGER` with `DROP ... IF EXISTS`, rewrite `CREATE TABLE` → `IF NOT EXISTS`, wrap `CREATE TYPE`/`ADD CONSTRAINT`/`ALTER PUBLICATION ... ADD TABLE` in `DO $$ ... EXCEPTION WHEN duplicate_object THEN NULL; END $$;`, and emit `DROP FUNCTION` only when a signature's return type actually changes.
- Gotcha when writing that preprocessor: matching the returns type with `RETURNS\s+([\w.]+(?:\s+\w+)?)` swallows the newline plus the following `LANGUAGE`, so identical return types compare as different and you emit spurious `DROP FUNCTION ... CASCADE` — which cascades away the `on_auth_user_created` trigger on `auth.users` and `riders_guard_update`. Use `RETURNS[ \t]+` and capture a single word.
- A correct replay of all 37 files yields: **34 public tables, 96 public policies, 35 public functions, 32 triggers (incl. `auth.users.on_auth_user_created`), 85 indexes, 7 realtime tables**. Verify against those numbers after any rebuild.

## Rider Android app (Capacitor)
- Built with **Capacitor 8**, package `com.yenego.rider`, app name `የኔ Go Rider`. It is a **WebView shell**: `capacitor.config.ts` sets `server.url = https://ligodelivery.vercel.app`, so the APK ships **no JS bundle** (`android/app/src/main/assets/public` holds only icons/fonts). Web changes go live without a new APK; a new APK is only needed for native config/plugin/permission changes.
- **The APK is only as good as what `main` serves.** Because the shell loads `server.url` (production), every rider-portal fix reaches installed apps *only once it is on `main` and deployed* — the APK ships no JS. A branch-only rider fix plus a freshly built APK looks finished but is **inert**: the installed app still runs whatever production has. This bit us — the v1.1 APK was built and hosted while `src/lib/native.ts` did not exist on `main`, so the background-geolocation plugin was never invoked and tracking still died when the phone was pocketed. Before claiming a rider fix is live, confirm it on the **production** bundle (fetch `/rider`'s chunks and check for a string literal like `minIntervalMs`), not just the local build.
- **Probing a deployed bundle for minified code: only string literals survive.** Function names (`openAppSettings`, `hasBackgroundLocationPermission`) are renamed by the minifier, and `import("@capgo/background-geolocation")` is rewritten to a hashed chunk path — so grepping for those returns false negatives and looks like the deploy failed. Grep for literals instead (`minIntervalMs`, `rd_tracking_title`, `when_in_use`), and confirm the dynamic chunks the entry references (e.g. `assets/esm-*.js`, `assets/dist-*.js`) return HTTP 200.
- Source of truth for the native bits: `capacitor.config.ts` (appId, server.url, PushNotifications presentation) and `src/lib/native.ts` (the bridge — dynamic plugin imports so the browser bundle never pulls in Capacitor; every helper no-ops when `Capacitor.isNativePlatform()` is false). `isNativeApp()` is what the web UI uses to hide install prompts inside the app.
- Permissions live in `android/app/src/main/AndroidManifest.xml` (fine/coarse + background location, foreground-service + `FOREGROUND_SERVICE_LOCATION`, camera, POST_NOTIFICATIONS, VIBRATE). Adding a permission means rebuilding the APK.
- **APK is hosted as a public GitHub release asset**, not Supabase Storage: `https://github.com/eyueltemesgen/ligodelivery/releases/download/rider-v1.1/yene-go-rider-1.1.apk`. The repo is public and the asset is just a signed binary (scanned: no keys, no service-role refs, no JS bundle), so a private bucket would add nothing while making the download unshareable. `rider.download.tsx` prefers `settings.rider_app.apk_url`, falls back to a short-lived signed URL for `apk_path` (only usable if the bucket is on a project we control), and finally to the baked-in `DEFAULT_RELEASE` public URL — so the page works before any admin row exists. Same reasoning as the baked-in public Supabase coordinates. **`DEFAULT_RELEASE` carries the version string the page displays, so bump it in the same commit as a new APK** or the page advertises the old build.
- **The download route is gated by `RiderGate`**, which is the real access control: signed-out → `/rider/login`; signed-in non-rider → "not a rider" + apply link; rider with `is_approved = false` → "under review" and **the download button is not rendered at all**. Verified both directions with `migration-tooling/verify_download_page.py`.
- Approved riders also get a `RiderAppPrompt` banner at the top of `/rider` (hidden in the native app and once dismissed). The `notifications` table has **no link column**, so the install prompt is shown in the portal rather than pushed as a notification link.
- Release signing is env-driven in `android/app/build.gradle` (`RIDER_KEYSTORE_PATH` / `RIDER_KEYSTORE_PASSWORD` / `RIDER_KEY_ALIAS` / `RIDER_KEY_PASSWORD`); without them the release variant is unsigned. The keystore lives **outside the repo** at `/workspace/rider-keystore/` with its password in `KEYSTORE_PASSWORD.txt` — back it up, because Android refuses to update an installed app signed by a different key. `android/` build output, `local.properties`, `*.apk`, `*.aab` and `*.keystore` are gitignored.
- **Background location now works** via `@capgo/background-geolocation` (MPL-2.0, free, Capacitor 8 — the community plugin stops at Capacitor v7 and Capawesome's needs a paid licence key). `native.ts` `watchPosition` runs the plugin when packaged and falls back to `navigator.geolocation` in a browser. Three things this depends on, each of which silently breaks tracking if changed:
  - `android.useLegacyBridge: true` in `capacitor.config.ts`. With the default bridge the plugin's callbacks stop after ~5 min in the background and the rider drops off the map while still shown as online. This is the plugin's documented Android fix.
  - Position writes go through `nativeRequest()` (`CapacitorHttp`) rather than Supabase's JS client, because Android throttles **WebView-initiated** HTTP after ~5 min in the background. `CapacitorHttp` is registered by the Capacitor bridge itself, so it needs no plugin entry.
  - The plugin needs a notification (`backgroundTitle`/`backgroundMessage`) — Android suspends a location foreground service without one. Strings are `rd_tracking_title`/`rd_tracking_body`.
  - `minIntervalMs` bounds the **native GPS request rate**, and its default is 0 which the service turns into **1 s** (`locationIntervalMs()`). With `distanceFilter: 0` that is a fix every second; set it to the portal's 5 s write cadence or the app burns battery on fixes it discards. Note `minIntervalMs` is *not* the JS-callback throttle — it also gates `LocationStore.shouldPost`, but that path returns early when no `url` is set, and we deliberately do not set one (writes go through `nativeRequest`).
  The foreground service (`BackgroundGeolocationService`, `foregroundServiceType=location`) and the permissions come from the **plugin's own manifest**, merged at build time — not from `android/app/src/main/AndroidManifest.xml`. Verify with `aapt2 dump xmltree --file AndroidManifest.xml <apk>`.
- Location permission is a **two-step** request in `requestLocationPermission()`: `["location", "notification"]` first, then `["backgroundLocation"]` separately, because Android 11+ refuses background in the same request. A background refusal leaves a working foreground-only app rather than failing. **`watchPosition` must call it before `start()`**: the plugin's `start({requestPermissions:true})` only ever requests `location` + `notification`, so without this call `ACCESS_BACKGROUND_LOCATION` stays declared-but-never-requested and tracking dies the moment the phone is pocketed — the foreground service still runs, so it looks fine until you walk away. (Verified in the plugin's Java: `requestLocationPermissions()` only chains the `location` and `notification` aliases.)
- **Requesting background location is necessary but NOT sufficient on Android 11+.** The OS ignores a programmatic request for `ACCESS_BACKGROUND_LOCATION`; “Allow all the time” can only be granted in Settings (the in-app prompt may only offer “While using”). So the portal also checks `hasBackgroundLocationPermission()` and shows the `rd_bg_loc_warn_*` banner with an `openAppSettings()` shortcut. Without that, a rider who never opens Settings silently gets foreground-only tracking. The check treats only `denied`/`prompt`/`when_in_use` as missing, so an unexpected value cannot nag a rider whose permission is fine, and it re-runs on `visibilitychange` so the banner clears after granting.
- **Verify the rider portal with a CDP stub, not just a build.** The Supabase storage key is `sb-<project-ref>-auth-token` with the ref from `src/lib/public-env.ts` (`kyfyljkxijmamnkhvqaw`) — a wrong ref leaves the page signed out and the portal renders empty. Pass `--remote-allow-origins=*` to Chromium or the CDP websocket handshake fails 403. The rider gate also calls `/auth/v1/user`, so a fetch stub must answer that or the page falls back to the apply screen.
- `@capacitor/geolocation` was **removed** once the background plugin landed — two location plugins competing for GPS is a real risk, and nothing imported it. Do not re-add it.
- Push notifications are **not wired**: the Gradle log says `google-services.json not found ... Push Notifications won't work`. FCM is free but needs a Firebase project and that file added to `android/app/`.
- Build: `npx cap sync android` then `cd android && ./gradlew assembleRelease` with `ANDROID_HOME`/`JAVA_HOME` set (JDK 21, SDK 35/36). Verify with `apksigner verify` + `aapt2 dump badging` (expect `com.yenego.rider`, `minSdk 24`, no `application-debuggable`).
- **Bump `versionCode` in `android/app/build.gradle` for every rider-facing build.** Android silently refuses to install an APK whose `versionCode` is not greater than the installed one, and the rider sees a generic "App not installed" — so shipping a fix with an unchanged `versionCode` looks like a broken download. v1.1 is `versionCode 2`.
- **The Android toolchain does not survive an environment reset** (both JDK and SDK are gone, and `apt-get` then fails with `List directory /var/lib/apt/lists/partial is missing - Acquire (13: Permission denied)`). Restore with sudo: `sudo mkdir -p /var/lib/apt/lists/partial && sudo chmod 777` it, then `sudo apt-get install -y openjdk-21-jdk-headless unzip`, then unpack `commandlinetools-linux-*_latest.zip` into `/opt/android-sdk/cmdline-tools/latest` (needs `sudo chown` on `/opt/android-sdk`) and `sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.0.0"`. `/workspace` is preserved, so `node_modules` and the keystore survive; the SDK download is the slow part (~4 min).
- **APK verification snippets** (`BT=/opt/android-sdk/build-tools/36.0.0`): `$BT/aapt2 dump badging <apk>` for the package/version, `$BT/apksigner verify --print-certs <apk>` for the signer, and `$BT/aapt2 dump xmltree --file AndroidManifest.xml <apk>` to prove the plugin's service and permissions merged in. `unzip -p <apk> | strings | grep -c` for a secret scan (check for `service_role`, `sb_secret`, `ghp_`, `AIza`).
- Do **not** force-push or rewrite `main`: the repo is Lovable-connected, and `main` moves independently (a shallow local clone was already force-updated by a Lovable push mid-session). Publishing the APK as a GitHub **release** is additive and safe.
